# ADR-0004: Fail-closed confirmation for high-risk tools

- 状态：Accepted
- 日期：2026-10-31

## Context

Agent 会执行真实动作：取消提醒、未来会删除日历事件、发送邮件。误操作代价高。产品原则要求「高风险操作需确认」。同时不能假设应用永远不崩溃、用户永远会回应。

## Decision

- 工具定义声明 `requiresConfirmation`。
- Agent 在调用前发出 `confirmation_required` 事件，界面显示摘要卡片；确认通过 IPC 返回。
- 拒绝、5 分钟超时、用户取消运行、应用重启 → **一律不执行**。
- 拒绝也会产生一次 `status: denied` 的工具结果与日志，告诉模型不要重试。
- 确认状态只存在主进程内存，不持久化；重启后不存在「悬空待确认」。
- 确认卡片必须展示人类可读摘要（工具 + 提醒内容 + 时间），并允许展开原始参数。
- 高风险工具不能通过 UI/日志/其他 IPC 绕过确认。

## Consequences

正面：

- 最坏情况是「没执行」，而不是「误删/误发」。
- 审计日志能看到用户拒绝的行为。
- 不需要复杂的持久化状态机。

负面：

- 用户离开 5 分钟后回来，确认已失效，需要重新发起。
- 后台主动任务不能无人值守地执行高风险动作。
- 一次 run 内多个高风险调用需要逐个确认，交互略慢。

## Alternatives

- 直接执行 + 撤销：邮件发送不可撤销，风险不可接受。
- 把确认状态持久化：重启后 UI 可能展示过期确认，容易误点；收益低。
- 用模型判断是否需要确认：不可靠，必须由代码声明。

## Revisit

- 若未来出现真正的后台自动化（如自动归档邮件），增加「策略授权」而不是放宽确认。
- 阶段 4 发送邮件前，确认卡片需展示收件人、主题、正文摘要，并支持编辑。
